## B. 可讲的细节

1. **为什么「整条线全成功才算成功」**：多数工具给的是完成度百分比，而备考里最危险的就是自我安慰——三个阶段做成两个，百分比很好看，但那一轮其实没过。这里的选择是让成功成为预期，让**失败成为值得被看见的事件**（这条在源码注释里就是这么写的）。
2. **为什么配对按执行时间而不是印刷时间**：提前一周印出来不代表提前一周执行。配对看的是「计划什么时候做」，所以提前印刷不会改变归属的节点。
3. **为什么要「最少配对数」**：一个阶段至少要落到几条任务上才算数，否则「一个任务都没排」会被当成「全部完成」——空集合的「全部完成」不能当成节点完成。
4. **为什么已裁定节点不能改规则**：裁定一旦生效，改规则就等于改历史。可以改名（不影响语义），不能改范围与规则。
5. **为什么要有 6 种阻断规则**：信号不该无条件穿过整条线。比如失败信号遇到「尚未配对的节点」时该不该继续传，取决于用户想不想让后面还没开始的阶段跟着一起失败——这是策略，不是常量。
6. **为什么 ID 删除后还要留着**：如果删除即可回收，用户撤销一次删除就可能「得到另一条任务」——统计、配对、历史全错位。永久身份换来的代价是 ID 空间只增不减（上限 100 万条，够用很久）。

## C. 机制（它怎么运转的）

实例靠「所属目标 + 执行时间」归入某个阶段节点，区间左闭右开，执行时间取计划日期加提醒时刻（没有时刻就是当天零点）。节点完成只是过程事实：配对数达标且全部完成。真正的成败来自信号：到点的信号沿指定方向逐个投递给接收节点，每个接收节点可以按自己的规则阻断；一旦裁定就写死，连同该节点所有配对实例一起报废。独立实体的标识符在删除后依然保留，撤销只恢复原来那一实体。

## D. 语义规则与不变量

- 空配对不算完成；「全部完成」必须建立在至少一条配对上
- 裁定不可撤销；已裁定的节点只能改名
- ID 全局唯一且删除后不复用，历史任务引用的 ID 也保留
- 计划文件只交换配置；配对记录、信号与裁定只在完整备份里
- 末节点的检查信号固定向头传播且不可阻断

## E. 边界与坑

- 节点不自行过期：「完成」只是过程信息，成败由信号裁定。
- 成功与失败**都报废**实例，但不能合并——否则解释不了免做、认可、失格、验收否定这些不同结果。
- 未完成的被删任务不会变成完成；调整任务所属或执行时间会重新配对（裁定前）。
- 编辑主线范围只影响之后建立的配对。
