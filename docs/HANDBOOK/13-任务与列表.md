## B. 可讲的细节

1. **为什么类别不让用户填**：手填的类别会撒谎。程序能从「有没有提醒时刻」「是不是重复」推出来，就不该再让用户维护一个可能和事实矛盾的字段。类别不落盘，也就没有「迁移旧类别」这种历史包袱。
2. **为什么要有「宽限」而不是直接判失败**：迟到五分钟和没做是两件事。宽限把「还能抢救」量化成分钟，默认 0 意味着严格：过了计划块就算用掉。
3. **为什么定时任务不滚动到明天**：滚动会让列表里堆满过期红色，最后没人看。这里让「漏了」被记录，而不是被无限顺延。
4. **删除可恢复，但只能恢复原来那一条**：删除时把整份任务写进身份登记，恢复时要求逐字段一致。这样「手滑删掉今天所有待办」有最便宜的保险，同时不会把旧 ID 洗成一条新任务。
5. **白名单校验不是形式主义**：项目可以带自己的白名单，所以校验必须和全局一致，否则用户能通过项目绕过限制——这条注释写得很直白。
6. **为什么休息周期每天重算**：昨日的番茄数带到今早，会让第一段专注结束后就出现长休息。以本地日期为边界，同日换任务和重启仍保留节奏，次日从头累计；跨午夜时只更新计数，让已经开始的专注或休息正常继续。
7. **为什么番茄完成不勾选任务**：一项任务可能需要多轮专注，也可能比预估更早做完。番茄完成只结束这一轮计时，是否完成任务由用户手动确认，避免把计时结果当成实际产出。
8. **为什么完成时自动补足预计投入**：应用外完成的任务同样有投入，让用户回忆分钟数会增加完成负担。只补预计与实际之间的差额，可以承认这份投入，同时保留超出预计的真实计时；补足记录单独标明来源，避免混淆时间依据。
9. **为什么 MCP 查询要分页而界面不分页**：对话上下文是最贵的资源，`get_tasks` 默认 100 条、最多 100 条，逼调用方按项目缩小范围；界面在本机渲染全部任务并按项目分组，分页反而破坏「我还有哪些事」的整体感。
10. **为什么教学待办不能手动删改**：它的事实来源是课程或作业的安排。允许手改就会出现「课表说周一上课、待办却写着周三」的分裂；把所有权留给来源，改期就只是在两个视图里同步同一件事。

## C. 机制（它怎么运转的）

任务只有一种结构，所谓类别是从它自己的字段读出来的：有提醒时刻且（挂在习惯上或来自重复模板）算习惯，其余算普通任务；因此改字段会改类别，而删掉容器不会改写冻结的 `recurring`。界面不直接改数据：它把用户意图翻译成一个动作发下去，内核在整份数据上做校验、保护规则与身份登记，返回一张新快照，界面整体重绘。删除不是消失，身份登记把内容留成恢复记录；恢复要过同一道校验，保证 ID 不能被洗成别的实体。计划文件只交换安排，导入时按 ID 合并并保留进度，`replace: true` 才删掉文件不再提及的未完成项，已完成与教学待办始终留下。列表则有两套排序：对话侧按日期、优先级、创建时间分页读，界面侧按项目分组并让用户在三档排序间切换。

## D. 语义规则与不变量

- 每个任务实例必须有有效计划日期，精确时刻可选
- 类别不存储、不可编辑，永远由 `reminderTime`、`habitId`、`recurring` 推导
- `recurring` 是生成时冻结的属性，不从当前模板反推
- 删除可按 ID 恢复同一实体，恢复内容必须与登记逐字段一致
- 历史 ID 不能转给另一种实体，也不能给新建实体复用
- 项目白名单 ≤100 条，且不允许空白与控制字符
- 过期任务不滚动，漏了就被记为漏了
- 番茄到时或提前完成只完成番茄，不自动勾选任务或步骤
- 勾选完成才按完成当时的差额补足预计投入；撤销完成只撤回补足
- 教学待办只能由来源更新；计划导出不含已完成任务与教学待办

## E. 边界与坑

- 类别是**推导**的，所以改字段（去掉提醒时刻）会改类别——这是设计，不是 bug，讲的时候要说清，否则会被当成不稳定。
- 宽限默认 0；习惯不计宽限（漏了就计一次缺勤），模板印出的习惯实例也把宽限写成 0。
- 项目白名单最多 100 条、每条 32768 字符；超限会在保存时直接拒绝。
- 单条任务最多 99 个预计番茄、200 个子任务；更大的事需要拆成多条任务。
- MCP `get_tasks` 单页最多 100 条，任务多时必须按项目或完成状态缩小范围。
- 「今日专注」只认 `dueDate === today`；逾期任务是另一件事，不会混进今天的时间线。
- 教学待办不能单独删除，也不能用计划文件改写；要调整请改课程或作业安排。
- 恢复已删除任务要求内容完全一致，不能拿旧 ID 写一条新任务；这是防 ID 洗白的硬约束。
