## B. 可讲的细节

1. **为什么类别不让用户填**：手填的类别会撒谎。程序能从「属于目标吗」「有提醒时间吗」「重复吗」推出来，就不该再让用户维护一个可能和事实矛盾的字段。这条也解释了为什么任务的类别在模板删掉之后依然正确——它当时就是推出来的。
2. **为什么要有「宽限」而不是直接判失败**：迟到五分钟和没做是两件事。宽限把「还能抢救」这件事量化成分钟，默认 0 意味着严格模式：过了计划块就算用掉。
3. **为什么定时任务不滚动到明天**：滚动的结果是列表里全是过期的红色，最后没人看。这里让「漏了」被记录，而不是被无限顺延。
4. **删除可恢复**：删除会连同数据一起进恢复通道，而不是真的消失。对「手滑删掉今天所有待办」这类事故，这是最便宜的保险。
5. **白名单校验不是形式主义**：项目可以带自己的白名单，所以校验必须和全局一致，否则用户能通过项目绕过限制——这条注释写得很直白。
6. **为什么休息周期每天重算**：昨日的番茄数带到今早，会让第一段专注结束后就出现长休息。以本地日期为边界，同日换任务和重启仍保留节奏，次日从头累计；跨午夜时只更新计数，让已经开始的专注或休息正常继续。
7. **为什么番茄完成不勾选任务**：一项任务可能需要多轮专注，也可能比预估更早做完。番茄完成只结束这一轮计时，是否完成任务由用户手动确认，避免把计时结果当成实际产出。
8. **为什么完成时自动补足预计投入**：应用外完成的任务同样有投入，让用户回忆分钟数会增加完成负担。只补预计与实际之间的差额，可以承认这份投入，同时保留超出预计的真实计时；补足记录单独标明来源，避免混淆时间依据。

## C. 机制（它怎么运转的）

任务只有一种结构，所谓类别是从它自己的字段读出来的：属于某个目标就是目标管辖；有提醒时间且是重复的，算习惯；其余是普通任务。因此改变挂载会改变类别，而删掉容器不会改写历史类别。界面这一侧不直接改数据：它把用户意图翻译成一个动作发下去，内核返回一张新快照，界面整体重绘。

休息周期跟着当天完整完成的专注累计。每次专注结束，先按实际结束日期对齐当天计数，再加一次；日期变化或旧数据没有日期时，从历史中重建。次日才恢复的旧计时先按原截止时刻收尾，再对齐现在的日期，避免把昨天的完成算进今天。

## D. 语义规则与不变量

- 类别不存储、不可编辑，永远由字段推导
- `recurring` 是生成时冻结的属性，不从当前模板反推
- 删除可按 ID 恢复同一实体，不会变成另一条任务
- 项目白名单条目 ≤100，且不允许空白与控制字符
- 过期任务不滚动，漏了就被记为漏了
- 休息周期按本地日期累计，同日跨任务共享；跨午夜专注按结束日期归属，跨日不打断已开始的计时
- 自动到时和提前完成只完成番茄，不自动勾选任务或步骤；提前完成计一次番茄，累计时长仍按实际用时
- 勾选完成任务才按完成当时的预计用时补差额；修改完成后的设置不追溯历史。补足归完成日，撤销完成撤回补足，删除任务保留历史；加载旧已完成任务不自动补足
- 首页待完成固定分组：今日定时 → 待补队列 → 今日未定时 → 无日期任务；按日期/提醒时间或优先级/创建顺序排序，不跟随全部任务页的排序选择（`src/main.ts`：`focusPage` / `todayTaskGroup` / `taskList`）。待补默认显示全部，无日期默认折叠；展开状态在本次应用会话保留，折叠任务仍计入总数。此前日期仍有效的非定时任务保留在今日未定时组。

## E. 边界与坑

- 类别是**推导**的，所以改字段（挂到目标、去掉提醒时间）会改类别——这是设计，不是 bug，视频里要说清，否则会被当成不稳定。
- 宽限默认 0；习惯永远是 0（漏了就计一次缺勤）。
- 项目白名单最多 100 条、每条 200 字符。
