## B. 可讲的细节

1. **核心不是「信任模型」，而是「可验证的落地」**：审阅用的是和执行完全同一套预检——如果审阅说没问题，应用时就不会用另一套规则再判一次。前后不一致才是「AI 改坏数据」的真正来源。
2. **双指纹**：导出时记下来源指纹，应用前再核一次。中间你手动改了两条任务，它就会拒绝这份文件让你重新导出——这是保护你，不是为难你。
3. **补丁是原子的**：200 项里错一项，整份不写。这样不会出现「改了一半」的中间态。
4. **分段读取**：整库塞进上下文既贵又容易丢重点。JSON Pointer 让你只取那一段。
5. **MCP 两个方向都用同一条底座**：对外暴露的 `--mcp` 不另起数据库，连的是正在跑的实例——所以它看到的永远是你看到的数据。
6. **为什么不给外部客户端紧急退出**：外部客户端可能是别的软件、别的模型。留给你自己按。
7. **为什么自动唤醒不加载 MCP**：MCP 服务器可能是会下单、会预约的真实系统。无人确认时唤醒它，风险不对称。

## C. 机制（它怎么运转的）

改数据这件事走文件：先导出一份带来源指纹的文件，分段读取，用受限的 JSON Patch 原子批改，再跑一遍与实际执行同一套预检生成差异，等用户批准后才落库——落库前再核对一次指纹，中间被改过就拒绝。MCP 有两个方向：助手可以调用用户配置的外部服务器；软件自身也能作为服务器被外部客户端调用，而那套桥接不另起数据库，连的就是当前实例。

## D. 语义规则与不变量

- 一次补丁最多 200 项，且全部成功才写盘
- 应用前重新核对来源指纹与文件哈希，数据变过就拒绝
- 文件 ≤20MB；单次读取结果 ≤256KB
- 外部 MCP 客户端不能触发紧急退出；严格保护与不可逆裁定照旧生效
- 异常自动唤醒不加载任何 MCP 服务器

## E. 边界与坑

- 计时/锁机未结束时不能应用工作文件。
- 文件 ≤20MB；单次读取 ≤256KB；界面最多展示前 100 项差异。
- 数据一变，旧文件作废（拒绝而不是猜测）。
- 外部客户端不能触发紧急退出；严格保护与不可逆判定照旧生效。
