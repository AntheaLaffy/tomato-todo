## B. 可讲的细节

1. **删除仍保留身份**：旧专注历史可能引用已经删掉的任务。保留 ID 可以避免新任务继承旧历史，也让「撤销删除」找得回同一段记录。
2. **恢复需要原始内容**：撤销是找回同一实体，不能借恢复入口把一个旧 ID 用在任意新任务上。比较的是规范化序列化后的整串 JSON，连字段顺序都参与，所以「差不多一样」不算一致。
3. **步骤使用局部编号**：步骤只在所属任务内寻址；它不是独立实体，不占用全局身份登记，也不会因为两个任务都有 `step-1` 而冲突。
4. **本地转换与交换文件分开**：本地存储可以明确识别旧结构并一次性转换；交换文件需要满足当前契约，避免旧配置被静默忽略。所以 v3 的本地文件能升级，v3 的导出文件会被拒绝。
5. **为什么类型也算身份**：一个 ID 如果从任务挪去当模板，旧会话里的 `taskId` 就会指向一个完全不同的东西。类型检查把这种「历史错位」挡在提交前。
6. **为什么核对在克隆上做**：身份合并会改动退役状态与恢复记录；如果校验失败却已经写进内存，下一次保存就会把坏状态固化。克隆加统一提交让失败等于没发生。

## C. 机制（它怎么运转的）

每次动作先走预检：在数据的克隆上应用动作，再把动作前后的活跃实体集合与已有身份表合并。合并时先给所有活跃实体补登记，再把旧身份表与动作带来的身份表按 ID 取并集；同一 ID 类型不同直接拒绝。随后把「动作前活跃、动作后消失」的条目标成退役，任务还会顺手把消失前的完整序列化结果写进恢复记录。最后对新活跃集合逐项检查：撞上退役记录且不是正在恢复的同一任务，就拒绝；通过后校验整张身份表，成功才落盘。

恢复走的是同一个入口，只是多了一步：预检先从登记里找这个 ID，要求它已退役、类型是 task，并且登记里的恢复内容与本次传入任务序列化后完全一致；满足后把它标回活跃并清空恢复记录。本地文件打开时先过 `readLocalData`：只有 `version === 3` 才做一次性改造，改造完统一按当前 `AppData` 严格解析；解析失败时原文件保留，调用方不会覆盖。计划导入则完全是另一条路：它先按 v6 校验计划，再合并配置与任务，最后仍要过同一套身份核对，所以「导入一个退役 ID」会被拦下。

## D. 语义规则与不变量

- 不同类型也不能共用 ID；删除不回收 ID。
- 已退役 ID 不能用于新建或导入其他实体；恢复只能恢复登记中的原任务。
- 恢复内容必须与原任务规范化序列化后逐字节一致。
- 计划 v6 不携带身份登记；完整备份携带，导入时与本地历史合并而不是替换。
- 候选动作校验失败不写入；落盘只在预检成功后发生。
- 子步骤编号是局部编号，不属于独立实体登记。
- 本地 v3 → v4 只对本地存储生效；交换文件按当前格式严格校验。

## E. 边界与坑

- 计划文件只有 v6；1–5 不会自动升级，直接拒绝并提示按新格式重新导出。
- 本地迁移只认数据版本 3；版本 4 直接严格解析，损坏或字段不认的文件会带着原文件报错。
- `restoreTask` 的 JSON 键序参与比较；手改备份里的这段字符串很可能因为键序不同而无法恢复（本地迁移会重算，外部文件不会）。
- 身份历史最多 100 万条，超出后保存被拒绝。
- 计划合并不能改写教学待办，否则整次导入失败。
- 删除项目不会回收项目 ID；它下面的任务保留，只是 `projectId` 被清空。
