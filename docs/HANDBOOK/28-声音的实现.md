## B. 可讲的细节

1. **为什么用合成而不是音频文件**：不打包素材、不受采样率与体积影响，频率表本身就是乐谱；代价是音色朴素——这与「关键节点轻声提示」的定位一致。
2. **为什么只有五个 cue**：声音只给「需要抬头」的时刻。开始、暂停、完成、提醒之外，勾选任务与切页不发声；学习期间也没有滴答声，滴答属于氛围而不是提示。
3. **为什么一次只响一个**：HUD 的 effect 是一条 `if / else if` 链，完成序号、起跑、暂停、提醒按固定顺序判断，第一个命中就返回。否则一轮自然结束可能同时满足「完成 + 自动开始下一段 + 提醒到点」，用户听到一串互不相关的铃。
4. **为什么看跃迁而不是看动作**：同一个 `startTimer` 既能从停止起跑，也能从暂停继续；按动作名判断会分不清。比较前后快照的 `running`、`paused`、`completionSerial` 与待提醒数量，才与「用户感知到什么」对齐。
5. **为什么音色选择不写进设置**：它只是这台设备上的听感偏好，换设备不该被同步，也不属于学习数据；所以走 `localStorage`，和皮肤偏好同一类。
6. **为什么音量要防抖**：拖动滑杆会每帧触发一次变更，每次都是一整份 `saveSettings` 落盘；400ms 防抖让磁盘只写「停手后的最终值」，同时本地增益已经即时跟手。
7. **为什么背景音与音效共用一套音量**：它们最终都汇到同一个 master 增益。把「音效音量」调小，背景音也会一起变小；想安静可以选 `silent` 或关掉声音。
8. **为什么音频失败可以被忽略**：声音是体验层的附加项。把它做成硬依赖，会让「没有音频设备」「浏览器拦截自动播放」的环境连计时都用不了；代码里所有入口都吞异常，只 warn 一次。

## C. 机制（它怎么运转的）

声音模块维护三个模块级状态：最新的设置镜像（开关、归一化音量、计时是否在专注）、用户尚未被快照确认的音量、以及背景音选择。HUD 是唯一「永远挂载」的番茄状态组件，它在每次快照变化时比较前后两张快照的计时状态、完成序号与待提醒任务数，命中某个跃迁就调用一次 `playCue()`；`playCue()` 再同步一次设置，确认声音开着且 context 已解锁，才把 cue 的音符表排进音频时间轴。背景音走另一条路：同一个 effect 调 `syncAmbientEngine()`，它按「声音开 + 专注在跑 + 非静音 + 已解锁」把引擎推进到播放或淡出状态，音色切换用交叉淡化。音量滑杆在事件处理器里直接改 master 增益，再防抖写回设置；设置页则走「编辑草稿 → 统一保存」。音频不可用、被策略拦下或用户静音，都只影响「有没有声音」，不影响任何状态变化。

## D. 语义规则与不变量

- 一张快照至多触发一个 cue：判断是一条 `if / else if` 链，宁可少响，不可连响。
- 第一张快照不发声；没有跃迁的重渲染不发声。
- 只有 `settings.sound === true` 才播放任何声音；缺失或 `false` 一律静默。
- 全应用只有一个 `AudioContext`；它只在用户手势之后创建或恢复，绝不自动创建后强行播放。
- 音量在播放层恒为 0–1；0 就是 master 增益 0，不存在「音量为 0 但仍有极轻反馈」。
- 背景音与提示音共用 master 音量与 `settings.sound`，不是两套独立设置。
- 停止或切换背景音必须淡出（0.6s），不得在非零振幅处直接截断。
- 任何音频错误都不得向调用方抛出，也不得阻塞计时、任务与页面渲染。

## E. 边界与坑

- 浏览器自动播放策略：首次手势之前的提示音会被跳过，这不是 bug；HUD 的起跑按钮会先 `ensureAudio()` 再发动作，靠这条顺序保证第一声能响。
- cue 名与实际语义有一处错位：从暂停继续**专注**时走的是 `start`，`resume` 只在非专注模式（开始休息）时播放；读代码时别按名字猜。
- 没有针对批量导入的专门静音分支：是否发声只看前后快照的跃迁。导入若让待提醒数量变化，提醒音会按同一条规则响。
- 背景音选择存 `localStorage`，隐私模式下只在本次会话生效；它不进备份，换设备后回到 `silent`。
- 音量 0 时节点仍会被调度，只是 master 为 0；这不会产生声音，但会照常创建并回收振荡器。
- 设置页的「试听」按钮是禁用占位；想确认音效只能真的开始一轮专注或触发提醒。
