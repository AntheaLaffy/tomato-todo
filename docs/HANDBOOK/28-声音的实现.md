## B. 可讲的细节

1. **为什么用合成而不是音频文件**：不需要打包资源、不受采样率体积影响，还能按参数微调（频率表就是乐谱）。代价是音色朴素——这与「关键节点轻声提示」的定位一致。
2. **为什么「学习期间不放滴答声」**：滴答声属于氛围音，不属于提示音。把它塞进提示体系，等于每次专注都在制造噪音。
3. **为什么一次只响一个**：若不加约束，一个阶段边界可能同时满足「专注结束 + 自动开始下一段 + 提醒到点」，用户听到的是一串互不相关的铃。选定单一提示并在注释里写明优先级，是刻意的取舍。
4. **为什么导入要静音**：导入会一次性改变大量状态，按逐条差异发声会变成噪音轰炸；而恢复数据本身也不该被当成「操作成功」来庆祝。
5. **为什么要区分方向**：勾选完成值得奖励，**取消**勾选不值得。用「未完成 → 完成」的方向判断，比用动作名判断更准（同一动作既能完成也能取消）。
6. **为什么淡出而不是停掉**：数字音频里把正在发声的信号从非零采样点直接切断，会听到咔哒声。先取消后续调度、再淡出，是代价最小的做法。
7. **为什么音效可以失败**：声音是体验层的附加项。把它做成硬依赖，会让「没有音频设备」的环境连计时都用不了。

## C. 机制（它怎么运转的）

每次拿到新快照时，界面先用「上一张快照 + 这一张快照 + 触发它的动作」三个输入算出**一个**提示（多数情况是空）：比较活动锁机、完成序列号、待提醒任务的 key、以及计时是否刚跑起来或刚停下。选中的提示交给音频层，音频层把对应的音符表排进一个 `AudioContext`，每个音符一个振荡器加一条个人增益曲线；被打断时先取消未触发的调度、再把正在响的按键淡出。背景噪声走另一条链路与另一个音量参数。整条链路对失败是容忍的：音频不可用、被浏览器策略拦下、或用户静音，都只影响「有没有声音」，不影响任何状态变化。

## D. 语义规则与不变量

- 一张快照至多产生一个提示；宁可少响，不可连响
- 导入、导入计划、载入示例这三种动作一律不发声
- 只有「未完成 → 完成」方向触发任务完成音；撤销不发声
- 声音被关闭、音量为 0、或音频不可用时，计时与任务逻辑不受任何影响
- 背景音与关键节点音效是两套独立设置，互不改变对方的音量
- 打断正在播放的提示必须淡出，不得硬切
- 可验证的两条（来自 `tests/audio.mjs`）：没有上一张快照、或两张快照完全相同 → **不发声**；`startTimer` 让计时由停转跑 → `start`，由跑转停 → `pause`，从暂停再跑 → `resume`

## E. 边界与坑

- 浏览器要求用户手势后才能播放音频：首次交互前的声音会被跳过，这不是 bug。
- 音量 0 等同于静音（选择函数直接返回空），因此不会出现「音量为 0 但仍有极轻反馈」。
- 三处实现分别负责「选哪个」（`sound-events.ts`）、「怎么发声」（`audio.ts`）、「界面何时调用」（`main.ts` 的 `accept()`），改动时不要跨层写逻辑。
