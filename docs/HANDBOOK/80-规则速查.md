把散在各章的规则写成可以直接引用的式子。记号沿用本手册约定：`x?` 表示可选、`[a,b)` 表示左闭右开区间、`⌈x⌉` 表示向上取整。每条规则后面给出实现位置与相关章节。

每条规则都有一个**规则 ID**（写在标题末尾，形如 `[rules.kind.derive]`）。其它章节引用规则时写 ID 而不是节号，这样调整本页顺序不会断链；ID 的写法与校验见 [00-读法与约定](00-读法与约定.md)。本页六个结构段（A–F）也各带一个 `rules.page.*` ID：它们只标示页面结构、不描述产品行为，供自查脚本识别标题，不要在其它章引用。

## B. 可讲的细节 `[rules.page.details]`

1. **为什么单设一页规则**：类别推导、提醒窗口、诊断阈值这些式子散在十来章里，各自写法略有出入；集中一页并给每条一个 ID，引用时就不必写「第 12 章第 2 节」这种一改顺序就断的定位。
2. **为什么用 ID 不用节号**：其它章引用的是 `[rules.window.pomodoro]` 而不是「第 2 节」。调整本页顺序、拆分或合并小节都不会断链；反过来，重命名 ID 等于删掉旧规则，检查脚本会立刻报出悬空引用。
3. **为什么公式写成伪代码**：伪代码能被逐行对应到函数。每条规则都标了函数名，读公式的人可以立刻跳到源码核对比较符；写「大约」「通常」这类词的规则没法核对，所以这里不写。
4. **为什么每条规则都指到具体函数**：规则不是自然语言承诺，而是可执行的判定。`windowMinutes()` 加不加休息、`tickReminders()` 用 `>=` 还是 `>`、`validateLock()` 按分钟还是按小时占位，差一格结论就不同，函数名是唯一的锚。
5. **为什么上界单独成表**：数量、长度、版本这些数字由校验函数集中拒绝，和阈值公式不是同一类东西；把它们排成表，改上限时只需要改一行，也不会把「校验拒绝」误读成「业务目标」。
6. **为什么结构段也带 ID**：`scripts/check-handbook.py` 要求本页每个二级标题都以规则 ID 结尾，否则把页面结构标题当成未定义规则。`rules.page.facts` 到 `rules.page.backlog` 这六个 ID 只为此存在，注释里也写明了不要引用。
7. **数字与文档的分工**：阈值以代码为准；`20 MiB` 这类只写在格式文档里的上限，会在第 8 条注明出处，避免把它当成代码已经拦截的事实。

## C. 机制（规则从代码到手册的路径） `[rules.page.mechanism]`

规则在代码里有三种形态：字段推导、纯函数公式、校验函数。字段推导最薄，`kindOf()` 读三个字段就决定类别；纯函数公式负责计算，`windowMinutes()` 算计划块、`band()` 算占用窗口、`diagnose()` 算容量与信号；校验函数负责拒绝，`AppData.validate()` 先把任务、计时器与容器逐项检查完，再调用 `validateLock()`、`validateBlocks()`、`validateTemplates()` 与教学、学习模块的校验。runtime 在每次动作分发前后都走同一套校验，所以 MCP 工具、HTTP 端点与界面写操作不会各自拥有一份阈值。写规则时先 grep 这些常量与比较符，再读函数体确认边界含不含等号，最后把函数名与章节写进 A 表；公式里的每个变量都能在函数里找到同名或同义赋值，找不到就说明这条规则已经过期，应在 F 段记下来。

## D. 语义规则与不变量 `[rules.page.invariants]`

- 规则 ID 只增不改：改名等于删除旧规则并新增一条，会断掉其它章的引用。
- 每条公式必须能指到一个真实函数或校验点；指不到就说明规则已经不存在，应当删除而不是保留。
- 阈值比较符以代码为准：`>` 与 `>=`、乘 100 再比较这类边界差一格就会改结论。
- 数量与长度上界同时出现在校验函数和格式文档里；两处不一致时以代码为准，并在 F 段记一条。
- `rules.page.*` 六个 ID 只描述页面结构，不得被其它章引用；`rules.guard.modes` 目前没有章节引用，但保留定义。

## 1. 类别推导 `[rules.kind.derive]`

```
habit(task) ⟺ task.reminderTime ≠ null ∧ (task.habitId ≠ null ∨ task.recurring)
kind(task)  = habit ? "habit" : "ordinary"
```

- 类别**不存储、不手填**，由上述字段推导；模板或习惯容器删掉后，历史任务仍按冻结的 `recurring` / `habitId` 读出当时的类别。
- 校验要求习惯实例必须有精确时间：`habitId = null ∨ reminderTime ≠ null`。
- 出处：`packages/core/src/model.ts` 的 `kindOf()`、`isHabit()`；`packages/core/src/lib.ts` 的 `validate()`；`packages/core/test/core.test.ts` 的 `habits_materialize_today_once_and_detach_on_delete`、`tasks_detach_without_being_deleted`。详见 [13-任务与列表](13-任务与列表.md)。`[T]`

## 2. 计划块与提醒窗口 `[rules.window.pomodoro]`

```
focus    = task.focusMinutes ?? settings.focusMinutes
sessions = max(1, task.estimate)
breaks   = Σ (i 从 1 到 sessions-1)  i mod longBreakEvery = 0 ? longBreakMinutes : shortBreakMinutes
window   = sessions × focus + breaks
有效窗口 = [start, start + window + (habit ? 0 : task.scrapMinutes))
```

- `reminderPending` 在 `start ≤ 现在` 时置位；到 `start + window + 宽限` 即过期。任务日期过去也过期，且此后不提醒、不滚动到明天。
- 宽限只给普通任务：计算时强制 `isHabit(t) ? 0 : t.scrapMinutes`；习惯实例本身要求有精确时间。
- 校验：`dueDate` 必填且有效、`reminderTime` 为 `HH:MM`、单次专注 1–180 分钟、`estimate` 1–99。
- 出处：`packages/core/src/reminders.ts` 的 `windowMinutes()`、`tickReminders()`、`validateReminderTask()`；`packages/core/test/core.test.ts` 的 `reminder_window_covers_multi_pomodoro_breaks_and_old_slots_stay_void`、`reminder_expires_after_its_planned_block`。详见 [12-课表与提醒](12-课表与提醒.md)。`[T]`

## 3. 当天休息周期 `[rules.timer.cycle.daily]`

```
cycle(day) = |{ s ∈ sessions : s.completed ∧ localDate(s.endedAt) = day }|
nextBreak  = cycle mod longBreakEvery = 0 ? longBreak : shortBreak
```

- 每次专注结束：先按实际结束时刻对齐日期（`refreshCycle(end)`），再记一条完成会话并 `cycle += 1`，由新的 `cycle` 决定长/短休息。
- 同日跨任务累计、同日重启保留；跨午夜的专注归结束日，次日恢复的昨日完成仍归昨日；新一天 `cycle = 0` 且计时未开始时，休息回专注待机。
- 跨日不打断运行或暂停中的计时。勾选任务时补写的 `taskEstimate` 会话 `completed` 为 false，不计入周期。
- 出处：`packages/core/src/lib.ts` 的 `refreshCycle()`、`finishTimer()`、`tick()`；`packages/core/test/core.test.ts` 的 `break_cycle_resets_at_local_midnight`、`focus_crossing_midnight_counts_on_completion_date`、`late_previous_day_completion_does_not_count_today`。详见 [13-任务与列表](13-任务与列表.md)。`[T]`

## 4. 上课时间（占用时段）的判定 `[rules.band.occupancy]`

```
band(block, date) = null                       , weekdayMonday(date) ∉ block.days
                  = [start, end)               , end > start
                  = [start, end + 1440)        , end ≤ start（跨午夜）
[b.start, b.end) = band(block, date)
overlap(block, date, s, e) = max(0, min(e, b.end) - max(s, b.start))
```

- 只有 `attention = "required"` 的时段参与冲突判定；`"light"` 时段正是并行作业该待的地方，不报警。
- 校验：名称 1–40 字符、备注 ≤2000 字符、星期为 1–7 且不重复、开始 ≠ 结束、最多 60 条。
- 出处：`packages/core/src/blocks.ts` 的 `band()`、`overlapMinutes()`、`requiredMinutes()`、`validateBlock()`；冲突判定在 `packages/core/src/diagnostics.ts` 的 `diagnose()`。详见 [12-课表与提醒](12-课表与提醒.md)。

## 5. 定时锁机时段 `[rules.lock.schedule]`

```
归属星期 = 时段开始那一天的星期
时长     = (end - start + 1440) mod 1440
约束     = 启用的时段在一周 7 × 1440 分钟的占位上两两不重叠
判定     = 只查今天与昨天两天的规则（覆盖跨午夜），命中的时段合并成 active
```

- 校验：最多 20 条、名称 1–40 字符、`HH:MM` 有效、开始 ≠ 结束、星期 1–7 不重复；`active` 的结束必须晚于开始且不超过 8 天。
- 结束一次快速锁机只把 `suppressedUntil` 推到**当前时段末**，不影响后面无关的时段。
- 出处：`packages/core/src/lock.ts` 的 `validateLock()`、`scheduledAt()`、`releaseLock()`；`packages/core/test/core.test.ts` 的 `scheduled_sleep_crosses_midnight_and_does_not_count_as_focus`、`invalid_schedules_are_atomic_and_restoring_backups_does_not_arm_locks`、`ending_a_quick_break_does_not_cancel_the_upcoming_sleep_window`。详见 [11-定时锁机](11-定时锁机.md)。`[T]`

## 6. 诊断阈值 `[rules.diag.thresholds]`

```
容量 = 用户填写的每日预算
     ? 近 28 天中 ≥5 个活跃日（≥20 分钟）的中位数（下限 30）
     ? 每日番茄目标 × 单次专注

超载     : 今天起 3 天内任一天，剩余预计分钟 × 100 > 容量 × 130
安排过少 : 只看明天；有历史基线且非空，预计分钟 × 100 < 容量 × 30
投入下降 : 近 7 天活跃日 ≥3，且合计 × 100 < 基线 × 活跃日数 × 40
习惯缺席 : 近 7 个完整日期中 安排 ≥4、缺席 ≥3 且 缺席 × 100 ≥ 安排 × 50
深夜记录 : 近 7 天有 23:00–06:00 结束记录的不同日期 ≥3
```

- 全部为本地规则，**不调用模型、不自动裁定**；每条信号带证据与一个反问句，结果按 key 排序、最多 30 条。
- 「活跃日」是当天有记录且 ≥20 分钟；「基线」是这些活跃日的中位数，是证据而不是可用时间。
- 出处：`packages/core/src/diagnostics.ts` 的 `diagnose()`；深夜不伪造专注由 `packages/core/test/core.test.ts` 的 `completing_tasks_at_night_does_not_fabricate_late_focus_sessions` 间接背书。详见 [17-诊断与统计](17-诊断与统计.md)。

## 7. 保护强度与严格模式 `[rules.guard.modes]`

```
allowed(窗口) =
    true                      , 窗口.pid = ownPid
    true                      , protection.mode = off
    false                     , protection.mode = lock（白名单被忽略）
    窗口.appId ∈ whitelist     , protection.mode = whitelist（逐项精确匹配、区分大小写）

strictProtected = (lock.active ≠ null ∧ lock.active.strict)
                ∨ (timer.running ∧ timer.mode = focus ∧ protection.mode ≠ off ∧ protection.strict)

desiredGuard    = 锁机命中 ? lock(白名单 = [])
                : 专注运行且 mode ≠ off ? lock(mode = whitelist ? 有效白名单 : [])
                : unlock
```

- 严格保护时 `apply()` 直接拒绝一切提前结束与修改；非严格保护中只放行 `emergencyUnlock` 与 `completeFocus`；休息锁机只允许紧急退出。
- 「锁定模式忽略白名单」由 runtime 决定：`desiredGuard()` 在锁机时下发空白名单，guard 的 `allowed()` 因此只放行 guard 自己的进程。
- 出处：`packages/core/src/guard.ts` 的 `allowed()`、`packages/core/src/lib.ts` 的 `strictProtected()` 与 `apply()`、`runtime/src/server.mjs` 的 `desiredGuard()`、`crates/guard/src/guard.rs` 的 `allowed()`；`packages/core/test/core.test.ts` 的 `strict_focus_rejects_every_early_exit_in_both_modes_and_recovers_at_deadline`、`protection_rejects_mutations_until_emergency_or_completion`，`crates/guard/src/guard.rs` 的 `whitelist_matches_exact_app_ids_and_own_process`、`empty_whitelist_is_strict_lock`。详见 [10-锁与专注保护](10-锁与专注保护.md)。`[T]`

## E. 边界与坑 `[rules.page.pitfalls]`

- 这些公式是**当前实现的摘要**，不是兼容承诺；权威在代码与 [../PLAN_FORMAT.md](../PLAN_FORMAT.md)、[../BACKUP_FORMAT.md](../BACKUP_FORMAT.md)。改语义时先改代码与格式文档，再回来改公式。
- `20 MiB` 是格式文档写的文件上限，代码没有按字节拦截：HTTP 请求体另有 1 MiB 上限（`runtime/src/server.mjs` 的 `MAX_BODY`），CLI 的 `scripts/import-backup.mjs` 直接读文件、不设这个限制；超大文件会先被读进内存，再靠 JSON 解析与结构校验拒绝。
- 严格保护连 `emergencyUnlock` 也拒绝：`apply()` 在严格检查处直接抛错，只有锁机到点或桌面执行后端故障才能解除；不要按「非严格」的经验去解释严格模式。
- 锁机重叠是按分钟占位，跨午夜规则用**开始日**的星期；改星期或起止时间后必须整表重算，单独改一条可能和别的时段撞上。
- 诊断的容量是预算，不是「这一天有多少空」；计划超量与安排过少可能同时出现在不同日期，别把两条信号当成互相矛盾。
- 规则的引用检查只看 ID 是否存在，不检查语义是否还贴切；删掉一条行为后，记得把 D 段公式与其它章的引用一起删。

## F. 待补与更新点 `[rules.page.backlog]`

- 规则页的函数名会随重构漂移；每次改 `packages/core/src` 的公式或校验函数后，按 A 表逐条核对一次。
- `rules.page.*` 六个结构 ID 是 `scripts/check-handbook.py` 要求「本页所有二级标题带规则 ID」的产物；若检查脚本将来放行结构标题，可以删掉它们。
- `rules.guard.modes` 目前没有被其它章引用；保留定义，等锁与专注保护章下次改版时再决定是否在正文引用。
- 教学与考试的时间窗口（上午/下午课程、晚间留给作业）目前只在 `packages/core/src/education.ts` 的校验里，尚未收进本页；需要时再新增规则 ID。
- `20 MiB` 的文件上限只有文档约定，没有代码拦截；接入实际大小检查后，把第 8 条的出处改成 runtime 的实现位置。
