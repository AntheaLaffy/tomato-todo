## B. 可讲的细节

1. **习惯和「每天重复的任务」差在缺勤**：重复让一次错过成为「缺勤」，而一次性定时任务只是约会，过了就作废。这条差别原来写在 Rust 注释里，重构后由统计的 `missed` / `voided` 分流和回归用例承担。
2. **为什么习惯本体这么轻**：习惯只管「哪些实例属于同一个习惯」，具体几点、周几重复是模板的事。这样改时间不用动历史，也不会有两处规则互相打架。
3. **为什么习惯不做补做**：能补做的习惯不是习惯。宽限恒为 0，过期即计一次缺勤——它是记录，不是惩罚。
4. **愿景为什么被请出任务体系**：它最早被设计成「开放性任务」——没有期限、可以一直做。后来发现这种任务只会把执行语义搅浑：算不算完成？漏了算不算失败？所以它被降级成纯标记：不补进度、不失败、不计缺勤。
5. **愿景为什么可以独立存在**：它既能是项目的激励，也可以是顶层的一句「考上某个学校」。它只承载一句话和一段正文，不参与任何算法。
6. **为什么删习惯不重写历史**：已生成的实例冻结了「来自周期印刷」这一事实，删除容器只清引用。否则用户整理一下习惯列表，过去的缺勤就会集体消失，统计也就不可信了。
7. **为什么界面只改第一个时段**：这是刻意的保守：多时段编辑还没有完整交互，保存时把其余时段原样带回，至少不会因为换个名字就悄悄丢时段。

## C. 机制（它怎么运转的）

新建或编辑习惯时，核心同时写两份数据：一份是只有 id 与名称的习惯组，另一份是 id 为 `habit:<习惯 id>` 的模板。模板固定为每周规则、自动印刷、预印 0 天，形状里的 `habitId` 指回习惯组，重修窗口被固定为 0。之后每秒 tick 调用的滚动印刷会读取这条模板：它先把本周所有配置过的星期展开成日期，跳过已过去的日期，再按账本补上本周剩余的日子；所以周五建、且周末也排了时段的习惯会立刻出现周五、周六、周日的实例，而下周要等新的一周开始才生成。

实例到期后由提醒推进置为过期：习惯没有重修窗口，计划块一结束就算消耗。过期未完成的实例不能勾选，统计按分类分别记缺勤或作废；删除习惯或把实例移出习惯组只会清掉容器引用，实例冻结的 `recurring` 仍在，所以历史分类和缺勤不会随容器变化。愿景是另一条完全独立的表：保存与删除都只动 `visions`，项目删除时顺带删掉挂在它下面的愿景，其余地方只把它当展示用的一句话。

## D. 语义规则与不变量

- 重复才让一次错过成为缺勤；一次性定时只是约会，过期记作废。
- 习惯宽限恒为 0、不补做：过期即记缺勤，过期实例不能勾选完成。
- 习惯实例必须有精确时间；形状里的重修窗口对习惯一律归零。
- 把实例移出习惯组不改写 `recurring`，历史分类与缺勤不随容器变化。
- 删除习惯会删掉它的模板，但保留已生成实例及其冻结来源。
- 愿景不补进度、不失败、不计缺勤；删除所属项目时一并删除，独立愿景保留。

## E. 边界与坑

- 习惯名称 1–40 个字符；时段不能为空、不能重复、时间必须合法，习惯的每个时段都必须带时间。
- 习惯漏做**不会补做**，只记缺勤；过期实例勾选会直接被拒绝。
- 习惯窗口只覆盖本周：周五新建会补齐本周剩余安排，但不会提前生成下周。
- 界面编辑习惯只改第一个时段，其余时段只能在提示里看到「保持不变」。
- 愿景不出现于待办、统计或提醒；不要期待它有任何自动行为。
- 删除项目会**物理删除**该项目下的愿景（不是把 `projectId` 置空），独立愿景不受影响。
- 习惯最多 500 条；习惯模板与普通模板共用 5000 条模板上限。
