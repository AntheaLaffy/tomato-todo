## B. 可讲的细节

1. **信任边界从「谁在执行」变成「谁拥有对话」**：旧版里番茄自己持有模型、凭据与提示词，所以要管密钥、登录与网络出口。重写后 runtime 不再持有这些，模型与凭据属于 DSH；番茄只守住数据与本机 API。
2. **为什么 runtime 干脆不联网**：域、数据与计时全在本机，联网能力只会扩大攻击面。需要对话的地方交给 DSH，番茄留下的是「数据不出机器」这条可以当卖点的边界。
3. **为什么 MCP 拒绝浏览器 Origin，而只读 API 放行 DSH Origin**：浏览器页面可以被诱导发起请求（CSRF 一类），所以写操作只走「带 token 的 MCP」；DSH 面板 UI 只需要读快照，于是只读端点对 DSH 的 Origin 放行，写端点仍走同一白名单。两条路，两种信任强度。
4. **为什么 token 单独成文件（connection.json 形状沿用）**：stdio 代理与 HTTP 桥共用同一套认证，stdin/stdout 上没法握手，所以把地址与令牌写进文件。token 与数据同处一个受保护目录，不进入任务备份。
5. **为什么「内置模型登录」整个消失**：模型的配置、额度与登录是 DSH 的职责。番茄再持有一套凭据等于同一个秘密维护两份，删掉内置助手时一并删掉了这份负担。
6. **为什么对外通道全部压到回环地址**：三个端口（runtime 43987、guard 43988、DSH 界面 3080）都在 `127.0.0.1` 上对话，配合 Origin 白名单与 token，本机浏览器页面里的任意脚本就够不着写操作。
7. **为什么共享库是上界而不是「二选一」**：用户一次授权整个学习目录后，项目仍可能需要更窄的范围（只给某一科）。把共享库当上界，项目授权只能收窄，既不用为每个项目重复授权，也不会让旧的项目级授权绕开用户这次明确选择的边界。取消共享授权不删除项目授权，是因为项目授权是另一次独立的用户动作，不该被一次批量取消顺手抹掉。

## C. 机制（它怎么运转的）

数据分三类，处理方式完全不同。第一类是**业务数据**：任务、统计、设置，只有一份计划 JSON，只在本机流动，写入是原子的。第二类是**凭据**：番茄这一侧只剩 MCP token 与 guard token，分别放在数据目录与 guard 数据目录里；模型凭据不在这台进程里——对话的登录、额度与提示词全部属于 DSH。第三类是**发出去的流量**：插件 UI 的只读快照走带 CORS 白名单的本地 HTTP，助手的写操作走带 token 的 MCP，guard 命令走带 token 的回环通道——三者都不离开本机；真正离开本机的只有 DSH 自己管理的对话流量，而那条链路的留存策略由 DSH 与模型供应商决定，不是番茄的管辖范围。对外提供的唯一入口是 MCP：只监听回环、要求 token、拒绝浏览器来源，stdio 代理与 HTTP 桥共用同一套认证。

## D. 语义规则与不变量

- runtime 无内置模型：不加载模型、不持有模型凭据、不发模型请求
- 全部进程间通道只监听 127.0.0.1（runtime 43987、guard 43988）
- 写操作只经 Origin 白名单的浏览器写端点或带 token 的 MCP；`/mcp` 拒绝浏览器 Origin
- 计划 JSON 是唯一数据源，写入必须原子
- 模型凭据与对话流量归 DSH 管理，不进入番茄的数据目录与任务备份
- MCP token 与 guard token 不进入任务备份；应用本体无账号、无遥测
- 共享资料库是资料授权的上界；项目单独授权只能收窄到它内部的子目录
- 取消共享授权只删除共享文件；项目单独授权保留，没有单独授权的项目立即回落 403

## E. 边界与坑

- 这是**通道与权限层面的保护**，不是加密存储：同机器上有你身份的进程仍可能读到计划文件与 token。
- DSH 对话流量的留存策略由 DSH 与用户选择的模型供应商决定，番茄不控制。
- `connection.json` 与备份的隔离是契约要求；`export_backup` 的实现是否真的排除了凭据，待 runtime 落地后核对（见 F 段）。
- 共享资料库是应用层的读取范围，不是加密或进程隔离：同机器上有你身份的进程仍可能直接读目录。
