## B. 可讲的细节

1. **为什么时段必须手动不重叠**：重叠的时段意味着「这一分钟属于两个规则」，到了边界谁来解除就说不清。与其在运行时猜，不如在保存时就拒绝——一条错误提示，换掉整类诡异 bug。
2. **为什么星期按开始日算**：23:00–01:00 这种时段跨过了午夜，如果按结束日算，周一的作息会莫名其妙在周二生效。这条规则写在模块注释里，是刻意定的。
3. **为什么只看今天和昨天**：跨午夜时段在「昨天开始的」和「今天开始的」里都可能命中，多算一天没意义、少算一天会漏。两天的窗口刚好够，且每次判定付出的代价最小。
4. **为什么结束小憩要「抑制」而不是简单清空**：如果直接清空，用户结束一次小憩就可能把当晚原本排好的作息时段一起跳过。抑制时间只推到当前时段结束，保证「停这一次」不等于「停今天」。
5. **「锁定」和「严格」是两件事**：锁定是窗口状态，严格是写前预检拒绝提前解除。定时锁机可以只有前者，也可以两者都有——所以字段里 `strict` 是单独一位，且真正的否决发生在 core，不在 guard。
6. **8 天上限**：一个活动锁机最多 8 天，防止算错时间导致用户被锁到下周。这是给自己留一个物理上限，而不是信任输入永远正确。
7. **为什么锁机计算留在 core、执行交给 guard**：时段判定是纯计算，能被单元测试逐分钟验证；全屏窗口、枚举前台窗口需要桌面会话权限。拆开之后 guard 崩溃不会带走时段与计时，runtime 还能按退避把它拉起来。
8. **为什么恢复备份不武装锁机**：备份是数据，不是「请立刻按这份作息开始锁屏」的授权。导入时把时段一律停用、活动锁机清空，用户需要自己重新打开——这避免了「恢复旧备份，机器突然锁死」这类最难解释的事故。
9. **为什么快速锁机不写规则表**：它是一次性动作，不是每周作息。写成规则会让「今晚早睡一次」变成永久负担，也会污染重叠校验。

## C. 机制（它怎么运转的）

锁机配置只描述「哪些星期、几点到几点不许用电脑」，本身不碰桌面。每秒的 tick 先做时间推进：活动锁机到点就清空；再用本机日期取出今天与昨天两套时段，把命中的规则合并成一段活动锁机；如果这一段与已有的活动锁机交叠，就取并集，避免切换瞬间闪一下。活动锁机存在时，计时被按在锁机开始那一刻结清，记录保留实际用时但不计番茄，随后回到专注待机；锁机期间所有写动作都被保护预检拦住，严格锁机连紧急退出与提前完成也不允许。runtime 不直接锁屏：它把「该不该锁、白名单是谁」翻译成 guard 的目标状态，只有状态变化才发命令，guard 用原生窗口接口建全屏窗，并每 600 毫秒把越界的前台窗口按回去。

## D. 语义规则与不变量

- 启用的锁机时段两两不重叠，保存时就拒绝
- 星期归属开始那一天；跨午夜时长按 `(end - start + 1440) mod 1440`
- 活动锁机总时长不超过 8 天；快速锁机 1–720 分钟
- 锁机开始时进行中的专注按实际用时结清为未完成记录，不计番茄
- 锁机时段本身不产生专注记录；锁机结束不自动重启专注
- 恢复备份不武装锁机：活动锁机清空、全部时段停用、定时自动开工关闭
- 严格锁机拒绝提前解除；只有桌面故障恢复路径能强制释放
- guard 只负责窗口与白名单，严格与否由 core 的写前预检决定

## E. 边界与坑

- 需要 runtime 保持运行。正常退出时，runtime 拉起的 guard 会被一并结束；若 runtime 被强杀，或 guard 是外部启动的独立进程，锁窗会留到 guard 自己退出或收到下一次 `unlock`。
- **电脑休眠时不唤醒**；恢复后若仍在时段内会继续锁，但锁机期间不产生任何专注记录。
- 后端覆盖 niri / Sway / Hyprland / GNOME / KWin / 原生 X11 / Windows / macOS；本机实测只覆盖 niri，其它桌面仍需各自会话验收（见 [10-锁与专注保护](10-锁与专注保护.md)）。
- 提醒在锁机期间到点就会进入 `reminderPending`（`tickReminders()` 不检查空闲），提醒条等空闲后显示；解锁不会自动切走 DSH 对话或把窗口置前。
- 快速锁机不受 20 条时段上限约束，也不参与重叠检查。
- 删除一个正在生效的时段不会解开当前锁机——正在进行的锁机只看活动锁机本身。
