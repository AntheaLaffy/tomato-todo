## B. 可讲的细节

1. **为什么时段必须手动不重叠**：重叠的时段意味着「这一分钟属于两个规则」，到了边界谁来解除就说不清。与其在运行时猜，不如在保存时就拒绝——一条错误提示，换掉整类诡异 bug。
2. **为什么星期按开始日算**：23:00–01:00 这种时段跨过了午夜，如果按结束日算，周一的作息会莫名其妙在周二生效。这条规则写在模块注释里，是刻意定的。
3. **为什么只看今天和昨天**：跨午夜时段在「昨天开始的」和「今天开始的」里都可能命中，多算一天没意义、少算一天会漏。两天的窗口刚好够，且每次判定付出的代价最小。
4. **为什么结束小憩要「抑制」而不是简单清空**：如果直接清空，用户结束一次小憩就可能把当晚原本排好的作息时段一起跳过。抑制时间只推到当前时段结束，保证「停这一次」不等于「停今天」。
5. **「锁定」和「严格」是两件事**：锁定是界面状态，严格是后端拒绝提前解除。定时锁机可以只有前者，也可以两者都有——所以字段里 `strict` 是单独一位。
6. **8 天上限**：一个活动锁机最多 8 天，防止算错时间导致用户被锁到下周。这是"给自己留一个物理上限"的设计。

## C. 机制（它怎么运转的）

一段锁机时段由「开始那天的星期 + 起止时刻」定义，跨午夜时时长按 `(end - start + 1440) mod 1440` 计算。判定当前是否在锁机中，只检查今天与昨天两套时段（这样才能覆盖跨午夜），命中多条时合并为一段。活动锁机一旦存在，优先级高于计时：开始那一刻就把进行中的专注结算掉。快速锁机是一种一次性的活动锁机，不写进规则表。

## D. 语义规则与不变量

- 启用的时段两两不重叠（保存时就拒绝）
- 星期归属开始那一天；跨午夜时长按 `(end - start + 1440) mod 1440`
- 活动锁机总时长不超过 8 天
- 结束一次快速锁机只抑制到当前时段末，不牵连后面无关的时段
- 锁机不计入学习时长；锁机结束后不自动重启专注

## E. 边界与坑

- 需要应用保持运行（可收进托盘 + 登录自启动）；**电脑休眠时不唤醒**，恢复后若仍在时段内会继续锁。
- 锁机结束**不会自动衔接**下一段专注——休息就是休息。
- niri / Wayland 与原生 X11 / EWMH 已实现锁定后端；X11 的快速锁机及接口失效释放已在 Openbox 隔离验证，各桌面会话仍需验收。
- 快速锁机上限 720 分钟，活动锁机总时长上限 8 天。
