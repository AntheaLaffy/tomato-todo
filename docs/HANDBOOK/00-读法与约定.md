# 读法与约定

> 手册章节 ｜ 最后核对：v0.8.2（2026-10-12）｜ 更新时机：新增章节类型、改动引用格式或自查规则时

这一章借用 [The Rust Reference](https://doc.rust-lang.org/reference/) 的组织方式：**先把「怎么读、怎么引用、什么算事实」定下来，再让每一章独立可读**。

## 这本手册是什么、不是什么

| | 内容 |
| --- | --- |
| **是** | 一份**面向读代码的人的参考手册**：当前实现的事实、取舍理由、推荐阅读顺序、关键结构与调用链、边界。每条事实带出处，能回到代码里核对。 |
| **是** | 与 [CODEMAP](../../CODEMAP.md) 配套的**说明层**：CODEMAP 说「改这个要动哪些文件」，本手册说「那些文件里的实现到底是什么」；两者的对照表在 [04-导航对照](04-导航对照.md)。 |
| **不是** | 上手教程：安装与使用看 [README](../../README.md)。 |
| **不是** | 设计说明：为什么这样分、这样取舍，看 [../DESIGN.md](../DESIGN.md)。 |
| **不是** | 文件契约：字段与范围的权威定义在 [../PLAN_FORMAT.md](../PLAN_FORMAT.md) 与 [../BACKUP_FORMAT.md](../BACKUP_FORMAT.md)，本手册只解释它们怎么被实现。 |
| **不是** | 承诺书：除第 20 章（数据与格式）这类明确标注为**契约**的章节外，其余章节描述的是**当前实现**，改动不视为破坏兼容。 |
| **不是** | 视频/文章素材：讲稿与拍摄清单在 `artifacts/publish/`（不入库），从手册取事实、在里面写台词。 |

**当文字和代码不一致时，以代码为准**，并在该章的 `F. 待补与更新点` 里记一条；这与 Reference「发现文字与实现不符就提 issue」是同一种处理方式。

## 两种读法

1. **回答一个具体问题**：先在 [03-概念索引](03-概念索引.md) 里找词，或按上面的覆盖表跳到那一章；每章开头都写了「一句话」与「读者会问的第一个问题」。
2. **通读一个方面**：从 [01-规模盘点](01-规模盘点.md) 或任意一章开始往下读，章内交叉链接会把你带到相关章节。

章节之间不要求顺序阅读。找文件、找符号、确定阅读顺序这类**导航信息统一放在附录** [04-导航对照](04-导航对照.md)（那是给维护者的），正文不塞文件清单。

## 约定（本手册用到哪些标记）

| 标记 | 含义 |
| --- | --- |
| **契约 / 规范** | 对外承诺的行为或格式，改动会导致兼容性问题；引用时要说明版本 |
| **实现记录** | 当前实现如此描述，可以随版本改动；引用时建议带一句「截至 v0.8.2」 |
| **未实现 / 明确不做** | 路线图里的事，或刻意不做的事；对外讲的时候必须与功能一起说 |
| **页眉** | 每章开头一行「最后核对：v版本（日期）」，表示这一章跟到哪个版本；检查脚本强制存在 |
| **出处** | A 表每行末尾的文件与函数；想核对某条事实，直接去那一行看 |
| **`[T]`**（行级） | 该条事实有单元测试直接背书；测试名见 [95-测试索引](95-测试索引.md) |
| **`验证：`行**（章级） | 每章页眉下方由 `scripts/handbook-tests.py` 生成，列出这一章由哪些测试文件覆盖（单元测试 / 端到端脚本），改测试会跟着变 |
| **规则 ID** | 形如 `[rules.kind.derive]`，定义在 [80-规则速查](80-规则速查.md)。引用规则时写 ID，不写节号——调整那一页的顺序不会断链，检查脚本会校验「引用的 ID 一定存在、ID 不重复」 |

**术语**：第一次出现时用引号标出，例如「待补」「缺勤」「报废」。这三个词是三种不同结果，最容易混，专门的对照写在 [16-习惯与愿景](16-习惯与愿景.md) 与 [12-课表与提醒](12-课表与提醒.md)。

## 规则 ID 的写法

- 形式：`rules.<分组>.<名字>`，全小写、点分层级，例如 `rules.kind.derive`（类别推导）、`rules.lock.schedule`（锁机时段）。
- 定义位置：只有 [80-规则速查](80-规则速查.md) 的二级标题末尾能定义 ID；其它章节只引用。
- 写法：正文里直接写 `[rules.…](80-规则速查.md)`，指向那一页而不是某个节号。
- 校验：`scripts/check-handbook.py` 会检查——每个 ID 唯一、格式合法、被引用的 ID 一定存在。这与 Reference 对「规则标识符在版本间可能变动」的告诫相反：我们要求它们**稳定**，因为手册自己引用它们。

## 每章固定的六段

| 段 | 用途 | 读代码时怎么用 |
| --- | --- | --- |
| **A. 事实** | 逐条列事实 + 出处；能用测试背书的会标 `[T]` | 想确认「到底是不是这样」，先看这里，再点开出处 |
| **B. 可讲的细节** | 每条回答「为什么这么设计、为什么不那样」 | 理解取舍，避免把刻意的设计当 bug 改掉 |
| **C. 机制** | 用一段散文说清这个域怎么运转（不含文件名与表格，读代码前先建立心智模型） | 先读这一段，再去看代码 |
| **D. 语义规则与不变量** | 这个域保证什么、什么情况下必须成立（规范性的清单，配上 [80-规则速查](80-规则速查.md) 的公式） | 改动前逐条核对，避免改出「看似合理」的回归 |
| **E. 边界与坑** | 做不到什么、容易误解什么、已知的取舍代价 | 改之前先看，避免改出「看似合理」的回归 |
| **F. 待补与更新点** | 未核对的、需要跑起来确认的；汇总在 [90-待补清单](90-待补清单.md) | 想继续挖就挑一条 |

## 维护约定

1. **改代码就改手册**：先动那一章的 A 表、C 段（代码路径）与 D 段（关键定义），再同步 [CODEMAP](../../CODEMAP.md) 与其它文档。CODEMAP 与手册的对应关系写在 [04-导航对照](04-导航对照.md)。
2. 核对完一章，把页眉的版本与日期改掉。
3. 三条命令都要过：`pnpm run check:handbook`（结构、页眉、出处、措辞、隐私）、`pnpm run handbook:stats`（规模数字）、`pnpm run handbook:tests`（测试索引）。
4. C 段里不出现仓库黑话与私人任务字样；引用会随版本变化的数字（技能个数、行数）时注明版本。
