## B. 可讲的细节

1. **「一个番茄钟为什么这么大」的答案**：不是界面多，而是**规则多**——主线判定、印刷账本、永久 ID、诊断阈值、保护与锁机的边界，这些都要有测试。3 万行里很大一部分是规则与它们的边界用例（`crates/core/src/tests.rs` 就 1,642 行）。
2. **Rust 做核心 + TS 做界面**的分工理由：状态机、校验、SQLite、统计放在 Rust，界面只做视图与声音。所以同一个逻辑不会在两边各写一遍。
3. **预览服务不是玩具**：它把同一核心暴露给浏览器，让开发能在浏览器里跑端到端测试（而不用启动整个桌面应用）。这也是为什么「预览里能用、装上不对」这种坑不存在。
4. **原生测试为什么要独立嵌套桌面**：它会真的开启窗口保护、抢焦点、全屏锁定。在你自己的桌面上跑，等于把测试暴力用在你身上——所以约束写成明文。
5. **助手测试用 mock 模型**：真实 SDK、流式工具调用与会话恢复都测，但不花用户额度。真实账号与桌面行为交给用户自测并写清复现方式。
6. **每次清理重建**：助手运行包不做增量合并，退役文件不会留下——和第 17 期的安装策略是同一条原则。

## C. 机制（它怎么运转的）

同一份 Rust 核心被两条前端复用：桌面壳与浏览器预览服务。界面层只做视图与意图翻译，业务规则不落地在界面里。质量靠四层验证堆出来：核心单元测试、真实浏览器端到端、隔离的嵌套桌面上的原生测试、以及用本机模拟模型跑的助手测试。发布由标签触发，产出安装包与压缩包；AUR 由模板单独渲染。

## D. 语义规则与不变量

- 业务规则只存在于 Rust 核心，界面不得自行实现一份
- 预览服务不能启用桌面保护
- 原生保护测试只在独立的嵌套桌面里跑
- 助手测试用本机模拟模型，不消耗额度
- 破坏性升级是明示策略：不自动迁移旧数据与旧备份

## E. 边界与坑

- 原生测试依赖较重（niri、Xvfb、tauri-driver、WebKitWebDriver、Python GTK），不是每条流水线都能跑。
- CI 只跑 Ubuntu 22.04；其他发行版由用户自测。
- 破坏性升级是明示策略：不自动迁移旧数据库与旧备份。
