## B. 可讲的细节

1. **为什么 guard 是独立进程而不是 runtime 的一部分**：锁窗、枚举窗口、系统通知都需要桌面会话权限；runtime 是 systemd 服务、跑 Node，独立出来之后 guard 崩溃不会带走计时和计划文件，runtime 还能按退避重启它。
2. **为什么「抢焦点」必须原生**：浏览器里的 JS 不能可靠把窗口带到前台；guard 用各桌面自己的窗口接口做激活，niri 走 `{"Action":{"FocusWindow":…}}`，X11 发 `_NET_ACTIVE_WINDOW`，Windows 走 `SetForegroundWindow` + ALT 重试，macOS 走 Accessibility 的 `AXFrontmost`/`AXRaise`。
3. **为什么 focus 只认 DSH 窗口**：guard 的 HTTP 端口虽然要 token，但把「任意窗口都能被拉到前台」暴露出去仍然太大；只匹配 `dsh-desktop`/标题里的产品名，目标固定、没有任意 id 参数。
4. **为什么桌面窗口优先于浏览器标签**：桌面窗口是应用自己的壳（关窗只隐藏、托盘常驻），浏览器标签可能同时开着多个；优先桌面窗口让「关窗继续跑」的模式下行为稳定。
5. **为什么锁机时不抢焦点**：锁机是用户明确选择的强约束；这时把 DSH 拉起来会让锁窗失去前台，等于绕过保护。`focus` 在 `State` 层直接返回 `None`。
6. **为什么首次 tick 不抢**：启动时可能已经有一堆历史 `reminderPending`，把它们当新事件会让 DSH 一启动就跳窗；基线只在 tick 之后比较增量。

## C. 机制说明

guard 的 HTTP 层只做三件事：鉴权、解析 JSON、把命令交给 `State`。`State` 只在内存里维护「是否锁定 + 白名单 + 后台 enforce 线程」；锁定开始时创建一个覆盖当前屏幕的锁窗，然后每 600ms 取一次窗口列表，看当前前台窗口是否属于本进程或白名单，不属于就把锁窗 focus 回去。它从不结束任何进程，也不写文件，进程退出即失去锁定，runtime 下次会话重新发命令。

`focus` 走的是另一条路径：`State::focus()` 先确认没有锁机，再让 `Desktop` 枚举窗口，按应用 ID / 标题筛出 DeepSeek Harness，必要时调用对应后端激活。runtime 的 tick 只负责发现「新提醒」与「一轮计时结束」两个跃迁，然后异步调 guard；前端 HUD 同时把 DSH 面板切到今日专注。窗口是否真的到前台由桌面环境决定：找不到窗口返回 `focused=false`，被前台策略拒绝则返回错误，但都不影响提醒与计时本身。

## D. 语义规则与不变量

- guard 不保存任何长期状态；进程重启后锁定不会自动恢复。
- 所有 `/guard` 命令必须带正确 token；token 错误一律 401。
- 白名单按 `app_id` 精确匹配；guard 自身 pid 恒放行；`lock` 模式忽略白名单。
- 锁机期间 `focus` 不生效；`lock` 时命令只替换白名单，不重建锁窗。
- `focus` 只接受 DSH 窗口（应用 ID 或标题匹配），没有任意窗口 id 参数。
- 回焦不结束、不挂起任何进程；它只改变前台窗口。
- runtime 的 focus 触发只发生在 `completionSerial` 或 `reminderPending` 数量增加的 tick。
- 找不到 DSH 窗口时 `focus` 返回 `{ok:true,focused:false,window:null}`，不是错误。

## E. 边界与坑

- Wayland 上未知合成器没有窗口接口，guard 会明确报「当前 Wayland 桌面尚无激活窗口接口」；niri/Sway/Hyprland/GNOME/KWin 才支持。
- Windows 的前台激活受系统策略限制；代码会在修饰键未按下时补发成对 ALT 重试，仍可能被拒绝。macOS 需要辅助功能权限，否则 `AXFrontmost` 返回错误。
- 浏览器标签的标题由 DSH 前端决定，必须含 `DeepSeek Harness`；如果用户用改过标题的包装器打开，可能识别不到。
- 同时开多个 DSH 窗口时只激活一个（桌面窗口优先），不保证每次都是用户想看的那一个。
- 锁机期间提醒不会抢焦点；这是有意的降级，不是 bug。
- 本机实测只覆盖 niri；Windows/macOS 代码保留在 guard 中，需各自平台验收。

## F. 待补与更新点

- GNOME/KWin/Sway/Hyprland 的 focus 路径仍以协议实现为主，缺少各自会话里的实拍验收。
- 多显示器时 `focus` 是否跟随目标窗口的工作区，需要在 niri 多输出环境确认。
- 若以后需要「在通知中心点击后置前」，要区分「用户点击通知」与「提醒到点」两条路径，后者不应无限重试。
