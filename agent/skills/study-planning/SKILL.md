先读 get_context 和匹配目标的 get_tasks。确认愿景/目标仍有意义、任务难度与当前掌握程度、固定课程/作息、可用时间和截止时间。缺少课表时问用户，不把历史专注时长当作全天容量。

get_context 的 `blocks` / `todayBlocks` 就是课表占用：`attention: required` 的时段要整段避开，`light`（水课）的时段签到即可、可以排作业或听别的课。没有这些数据时先问用户哪些课能并行，再用 `save_block` 补齐课表，别默认所有课都不能占用。

课表之外的外部约束（座位预约、图书馆开放时间、课程资源）如果用户配了对应的 MCP 服务器，用 `list_mcp_servers` 看清有哪几个再查证，别凭印象编；用到的数据要说明来自哪个服务器。

规划顺序：
1. 固定约束与休息先占位；保留一部分可用时间应对估时偏差，缓冲比例按用户反馈确定。
2. 按目标节点依赖和期限挑选关键下一步，已完成、作废、成功/失败已裁定实例不重新安排。未完成任务不自动累加到次日。
3. 描述可观察的成果，如“完成一组题并解释错因”；把长任务拆成用户可开始的段落。新任务估时给来源或注明待验证，避免凭空生成数量。
4. 学习方法与任务匹配：检索练习用于测掌握、间隔复习用于保持、错题复盘用于识别原因；不使用额外任务掩盖未解决的知识困难。
5. 检查番茄段数、每段时长、段间休息、提醒时刻、时区及目标节点边界。把作业排进 `light` 课程时段而不是 `required` 时段，不重复制造时间冲突。
6. 给出变更理由、假设、取舍和复盘时间。一般先调整未来一至三天，用户确认后扩大范围。

实施时读 tomato-files，优先计划 v5 导出编辑以保留历史。保持既有稳定 ID，按 Schema 补齐字段。任何计划都不能跳过软件的保护规则或不可逆裁定。
