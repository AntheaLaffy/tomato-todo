---
name: study-diagnosis
description: 分析番茄 Todo 的时段冲突、计划超量、习惯缺席、主线停滞或投入变化；用于异常唤醒与学情复盘，先核实误报和缺失记录再提出修改。
---

1. 调用 get_context，保留检测时间、涉及的任务 ID、统计窗口与预算来源。读取已确认记忆，不能用待确认假设解释异常。
2. 按影响选最多三项：近期硬性时间冲突优先于历史趋势。规则是提醒，不是裁定。历史活跃日中位数不是用户可用时间；每日番茄目标不是必须完成的总课时。
3. 只挑最相关的一两点，说清楚证据和替代解释：`blockConflict` 是排进了需专心的课时，可挪到 `light`（水课）时段或课后；普通 `collision` 可能是课内并行；超量可能是估时偏大或额外时间；习惯缺席可能是模板不合适或用户主动停止；主线停滞可能在等待条件或线下学习；深夜记录可能符合个人作息；投入下降可能是课程、记录方式或休息变化。不要把每种可能都列一遍。
4. 提出能改变决策的最少问题，一轮不超过三问，优先选择“估时是否准确”“是否仍重要”“这一天可用时间是多少”。没有回答时只给条件方案，不生成确定课表或补做大量任务。
5. 使用小步实验：调整一项任务的时间或颗粒度，指定何时复盘及观察指标（如实际专注分钟/按时开始率）。不追求清零任务数量，不修改成功/失败裁定。
6. 用户确认后切换 study-planning 与 tomato-files 生成审阅文件。将暂定原因通过 study-memory 存为待确认假设，注明证据来源。
7. 需要外部事实（座位是否约满、图书馆开放时间、课程资源）时，先 `list_mcp_servers` 看用户配了哪些 MCP 服务器，用它查证而不是猜；查到就说明数据来自哪个服务器，唤醒轮次没有这些工具，只提出来让用户确认。

回复时先给一句话结论，最多带一两个最相关的点，再给一个追问或条件方案；不要逐条罗列清单、不写小标题，也不要把规则报警次数当成用户表现分数。
